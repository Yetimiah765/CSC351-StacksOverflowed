# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # install dependencies
npm run dev        # start dev server (http://localhost:3000)
npm run realtime   # start the poker realtime relay process (connects to Supabase Realtime), separate process
npm run build      # production build
npm test           # run all tests (vitest)
npx vitest run __tests__/api/auth.test.ts   # run a single test file
```

## Environment setup

Copy `.env.example` to `.env.local` and fill in your Supabase credentials before running the app. `SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are read by `lib/supabase.ts` — either URL prefix works. Use the service-role key, not the anon key: none of the tables below have Row Level Security policies, and the auth routes read `players.password_hash` directly, so the anon key must not be relied on to protect that data. The browser, however, needs its own `NEXT_PUBLIC_SUPABASE_ANON_KEY` (distinct from the server-only `SUPABASE_ANON_KEY`) for the poker page's Realtime connection — only `NEXT_PUBLIC_`-prefixed vars reach the client bundle, and the anon key (never the service-role key) is the one meant to be shipped there. The poker room also needs `POKER_SERVER_SECRET` (any long random string, the same for the Next app and `npm run realtime`, never `NEXT_PUBLIC_`): it signs relayed poker actions and seals hole cards (`lib/pokerSecure.ts`).

## Architecture

This is a Next.js 14 App Router project with Tailwind CSS, backed directly by the Postgres schema in `supabase/schema.sql` (no Supabase Auth — see below). The poker room additionally runs its own Node process (`server/pokerRealtimeServer.ts`) that relays table state through a Supabase Realtime channel (Broadcast + Presence), separate from Next's HTTP server, matching `docs/architecture/C2.mmd`.

**Auth and profile data model:**
The schema (`supabase/schema.sql`) has no email column and no link to Supabase's built-in `auth.users` — it is entirely username/password based:
- `players` — one row per account: `player_id`, `first_name`, `last_name`, `birthday`, `password_hash`, `balance`, `bio`, `profile_photo` (BYTEA, PNG only), `account_status`.
- `usernames` — a player's username lives here, not as a column on `players`, so that a changed username can stay reserved for 24 hours (`is_current` / `reserved_until`).
- `player_sessions` — one row per player (`player_id` is UNIQUE), holding a hash of that player's current session token; a new login overwrites it, which is how a second login invalidates the first.

**Request flow for auth:**
1. `app/register/page.tsx` and `app/login/page.tsx` are `'use client'` forms that POST to the API routes via `fetch`.
2. `app/api/auth/register/route.ts` validates the SRS-101/102 field rules (names, username shape, password shape, minimum age — see `lib/auth.ts`), hashes the password with bcrypt, inserts into `players`, then inserts the username into `usernames`. If the username insert fails (lost a uniqueness race), the route deletes the just-created `players` row by hand, since two separate PostgREST calls can't share a transaction.
3. `app/api/auth/login/route.ts` looks up the current username (case-insensitively) in `usernames`, verifies the password against `players.password_hash` with bcrypt, rejects a `Pending Deletion` account, then generates a random session token, stores its SHA-256 hash in `player_sessions` (upsert on `player_id`, so logging in elsewhere invalidates the old session), and returns the raw token to the client.
4. The client stores that token in `localStorage` under `player_token` and sends it as `Authorization: Bearer <token>` on `/api/profile`, `/api/profile/avatar`, and `/api/profile/balance`. Those routes resolve it back to a `player_id` via `getPlayerIdForToken()` in `lib/auth.ts`, which hashes the token and looks it up in `player_sessions`. `POST /api/auth/logout` (the profile page's Log out button, SRS-105.1) deletes the `player_sessions` row matching the token's hash, and the client then clears `player_token`.
5. `lib/supabase.ts` — `getSupabaseClient()` returns `null` when env vars are missing; every route guards against this and returns a 500. Its client passes `cache: 'no-store'` on every fetch: Next 14 otherwise keeps server-side `fetch()` results (i.e. every supabase-js query) in its Data Cache, so a route Next treats as static — one that never reads the request, like `GET /api/players/[playerId]/avatar` — would serve its first query result forever.

**Profile:**
- `GET`/`PATCH /api/profile` read and update `players` + the current row in `usernames`. There is no "create profile" step — registration already creates the full `players` row, so `PATCH` takes any of `bio`, `firstName`, `lastName`, `username` (one per pop-up) and ignores everything else — notably any password field, since passwords change only through Change Password (SRS-112.2). `bio`: SRS-114.1/114.2, optional, 50 words max, empty stored as `NULL`. Names: trimmed, then the registration rules from `isValidName()` in `lib/auth.ts` plus `NAME_MAX_LENGTH` (50, the column size) (SRS-112.3). `username`: checked with `isValidUsername()`, then changed by the Postgres function `fn_change_username(p_player_id, p_username)` via `supabase.rpc` (migration `2026-10-19_change_username.sql`). In one transaction it locks the player's row, allows one change per 24 hours using `players.username_changed_at` (a capitals-only change counts but reserves nothing), deletes reservations that have run out (SRS-112.8), refuses a name that's current or reserved ignoring case, marks the old name reserved for 24 hours (SRS-112.7), and inserts the new current row. It returns `{ status: 'changed' | 'unchanged' | 'taken' | 'cooldown' | 'invalid' | 'not_active' | 'not_found' }`, which the route maps to 200/200/409/429/400/403/404. No password is asked for (SRS-112.5). Like the Daily Login Box function, its `EXECUTE` grant is revoked from `anon`/`authenticated`. Registration also deletes an expired reservation of the requested name before its taken-or-reserved check, so a released name can be signed up with. Word counting lives in `lib/bio.ts` (`countBioWords`, `BIO_MAX_WORDS`), shared by the API and the bio editor so their counts always match (SRS-114.5).
- `app/profile/page.tsx` lays out: the photo (`components/profile/ProfilePhoto.tsx`) with Log out underneath; first/last name, then username and password (dots only — only the hash exists, SRS-104.5) as boxes from `components/profile/ProfileField.tsx`; the bio; then `CosmeticsSection` and `StatsSection`. A field with a pencil opens a pop-up built on `components/profile/EditDialog.tsx` (Cancel/Escape discard, Save replaces and closes); the bio's is `BioEditor.tsx`, with a live "N / 50 words" count that turns red and disables Save past the limit; first name, last name and username use `TextFieldEditor.tsx` (one-line box, Save disabled while blank or unchanged, the server's error shown in the pop-up). The page's `saveField()` sends one field per `PATCH`. The password's pencil opens `PasswordEditor.tsx` (current password, then the new one typed twice; Save stays disabled until all three are filled and the two match, with a live "don't match" warning), which posts to `POST /api/profile/password`; on success the page shows a green "Your password has been changed." notice, cleared when any pop-up opens. `StatsSection` ("Money won/lost" / "Time played" tabs, totals then per game, dashes until games record results) is a placeholder until games record results. `CosmeticsSection` is real — see Cosmetics below.
- Clicking the photo opens a small menu: Upload new photo (which also replaces an existing one, SRS-115.4) and, only when there is a photo, a red Remove photo (SRS-115.6); upload/remove errors show inside the menu, and a click outside or Escape closes it. With no photo it shows `components/profile/DefaultAvatar.tsx`, a blank person icon (SRS-115.5) meant to be reused wherever a player's own photo is shown (the poker seats still use their own initial-letter fallback).
- `POST /api/profile/password` (Change Password, UR-113 — the only way a password changes, SRS-112.2) takes `{ currentPassword, newPassword, confirmPassword }`: the current password is required (SRS-113.1), the new one must pass `isValidPassword()` with the same `PASSWORD_RULES_MESSAGE` registration uses (SRS-113.3, both in `lib/auth.ts`), and the two new ones must match (there is no password reset, so a typo would lock the player out). Only then is the current password checked against `players.password_hash` with bcrypt (SRS-113.2) — a wrong one is a 403, not 401, so the page doesn't treat it as an expired session — and the new bcrypt hash saved. The player's session stays valid.
- `POST /api/profile/avatar` validates the upload is a PNG by file signature (not filename) and ≤5MB (SRS-115.1–115.3), then writes it straight into `players.profile_photo` as a Postgres hex-encoded bytea string; `DELETE /api/profile/avatar` sets that column back to `NULL` (no DB change was needed — `NULL` already means the default icon). Both routes and `GET /api/profile` convert that column to a `data:image/png;base64,...` URL for the client — there is no Supabase Storage bucket.

**Home page and nav bar:**
- `lib/games.ts` is the single list of games on the home page (SRS-107.1), each with a `tag` shown over its picture. A game with `href: null` is dimmed with "Coming soon"; setting `href` to the game's route makes it playable, and its links send guests to `/login` instead (SRS-108.3, via `playHref()` in `components/useSignedIn.ts`, which also holds the `useSignedIn()` hook that reads `player_token`).
- The home page (`app/page.tsx`) treats every game equally — no game is featured. Top to bottom: `components/HomeHero.tsx` (heading, plus signup/login buttons for guests or "Start playing" / "Claim free coins" for signed-in players), `components/GameGrid.tsx` (one card per game, the whole card a link), and a Daily Login Box promo linking to `/shop` (its coin range comes from `DAILY_LOGIN_BOX_REWARDS`). All pictures are inline SVG in `components/GameArt.tsx` — one per game, keyed by the game's `id` (a new game needs an entry in its `ART` map, or it gets a plain placeholder), plus `HeroArt`. There are no image files.
- `components/NavBar.tsx` is rendered on every page by `app/layout.tsx`, full width: Home and a cart (linking to `/shop`) at the left edge, the balance and a profile icon at the right edge. It re-reads `player_token` on every navigation and fetches `GET /api/profile/balance`, which returns only `{ balance, playerId, outlineArtKey }` because the full profile's photo can be several MB. For a logged-in player the profile icon is their photo (the 96px thumbnail from `GET /api/players/[playerId]/avatar`, fetched only when the player or photo changes; the blank icon if none) inside their equipped profile outline, a 40px photo in a 60px badge whose ring reaches about 48px across (SRS-120.7), and the balance pill gets a 1.5px gradient border and glow in that outline's colors from `OUTLINE_ACCENTS` in `lib/cosmetics.ts` (SRS-120.8; a test checks every outline has colors). `CosmeticArt` is loaded with `next/dynamic` there so the artwork module isn't in every page's first load. Guests see 0 coins (SRS-109.4) and the profile icon links to `/login`; a 401 clears the stale token.
- A page that changes the balance without navigating should call `notifyBalanceChanged()` (`lib/balanceEvents.ts`) afterwards; the nav bar listens for that event and refetches immediately (SRS-110.5, SRS-NFR-104). Likewise `notifyAppearanceChanged()` after a new profile photo or equipped outline (the profile page calls it), so the nav badge redraws within SRS-NFR-104's 2 seconds.
- The nav bar is `h-16`, with 48px icons and a 48px-tall balance pill, so pages use `min-h-page` (defined in `tailwind.config.js` as the window height minus 4rem) instead of `min-h-screen`.

**Cosmetic shop — Daily Login Box (UR-128):**
- `app/shop/page.tsx` shows the Daily Login Box first (`components/DailyLoginBox.tsx`), then the blind boxes (`components/BlindBoxShop.tsx`, see Cosmetics below).
- `GET /api/daily-login-box` returns `{ available, nextAvailableAt, msRemaining }` for the logged-in player, from their latest `daily_login_box_claims` row; a player with no rows can open a box right away (SRS-110.2). `msRemaining` is computed server-side so the countdown doesn't depend on the browser's clock.
- `POST /api/daily-login-box` picks the reward with `crypto.randomInt` via `pickDailyLoginBoxReward()` (`lib/dailyLoginBox.ts`: 250/500/750/1,000 coins at 40/30/20/10%; the database also still accepts the pre-2026-10-15 amounts 25/50/75/100 so older claims and not-yet-updated copies of the app stay valid), then calls the Postgres function `fn_open_daily_login_box(p_player_id, p_reward)` through `supabase.rpc`. That function does everything that must succeed or fail together (SRS-128.9) in one transaction: it locks the player's row (so simultaneous requests can't both claim, SRS-128.19), rejects non-`Active` accounts and claims inside the 24-hour cooldown, credits the balance, and inserts the claim with `next_available_at = claimed_at + 24 hours`. It returns `{ status: 'opened' | 'cooldown' | 'not_active' | 'not_found', ... }`, which the route maps to 200/409/403/404; an RPC error maps to 500 and nothing is saved (SRS-128.21).
- `fn_open_daily_login_box` has its `EXECUTE` grant revoked from `anon`/`authenticated` (only `service_role` can call it), because the anon key is public.
- The box's button says **Spin**. After the API reply (i.e. after the transaction has committed), `components/SlotReveal.tsx` pops up three slot reels that stop left to right on the reward (last one at 1.5 s), followed 250 ms later by the "+N coins" result (SRS-128.10). The reels use the `reel-spin` CSS keyframes in `app/globals.css`, which are timed by the clock rather than by redraws; the last reel's `animationend` (with a backup timer) marks the stop. The nav bar's balance is refreshed as soon as the API replies (SRS-NFR-104): the pop-up's backdrop (`z-50`, 90% opaque and blurred) covers the nav bar, so the new balance is ready behind it without spoiling the spin. The card also leaves the won amount unhighlighted until the pop-up closes. The page always rebuilds its state from `GET`, so a refresh mid-spin shows the cooldown instead of replaying the reveal (SRS-128.16/128.17).

**Blackjack (SRS-901 – SRS-911):**
- `lib/blackjack.ts` is pure and has its own 52-card deck and Fisher-Yates shuffle (it does not share `lib/pokerCards.ts`). A **round** (`BlackjackState`) is one Deal: `hands` (one `PlayerHand`, or two after a split, each with `cards`, `doubled`, `fromSplit`, `done`), `active` (the hand being played), `step` (moves so far), `dealerCards`, and `deck`. It has the bet rules (`BLACKJACK_CHIPS` 10/25/50/100, `MIN_BLACKJACK_BET`, `checkBlackjackBet()`), `handTotal()` (aces 11 unless that busts, SRS-905.1), `dealHand(bet, randomIndex, presetDeck?)` (player, dealer, player, dealer; a blackjack on either side ends the round at once), and `playMove(bet, state, move)` for the hand being played: Hit (over 21 busts; exactly 21 stands automatically), Stand, Double (SRS-910: first two cards of a hand, one card, the hand's bet doubled), and Split (SRS-911: once, on two cards of the same **rank**; makes two `fromSplit` hands dealt one card each, played in order; split aces take one card each and end). Once every hand is done the dealer plays once (`playDealer()`, draws on 16 or less, stands on any 17), unless every hand busted, and `settleHand()` settles each hand on its own bet (`handStake()`): a blackjack wins `floor(stake × 3/2)` but never on a `fromSplit` hand (SRS-911.5), any other win 1 to 1. `canDouble()`/`canSplit()`/`moveCost()` (another original bet for Double and Split) and `totalStake()` serve the routes. `handView()` is the only shape sent to the browser — per-hand `cards`/`total`/`bet`/`result`, `active`, `step`, `canDouble`/`canSplit`, `totalBet`, `net`, the dealer's second card as `null` and no deck until the round ends.
- **Rounds in play live in the Next server's memory** (`app/api/blackjack/hands.ts`, a `Map` keyed by player_id on `globalThis` so dev hot reloads keep it), because `blackjack_hands` has no columns for cards yet. A server restart forgets rounds in play, but each round's `blackjack_hands` row is opened when it is dealt (result/net/completed_at NULL, which the table allows) with `bet_amount` kept at everything staked (`saveStake` after Double/Split); `refundLostRounds()` in `record.ts` returns the stake of any open row with no round in memory and closes it as a Push. It runs on `GET /api/blackjack` (without taking the busy flag: skipped while busy, and only for rounds dealt over 30 s ago), before a deal, and on a move with no round (404 with `refunded`); the page shows a green notice. The row's `hand_id` is the round's `handId`. After a round ends the next deal waits `NEXT_HAND_DELAY_MS` (5 s, in `lib/blackjack.ts`), tracked per player in memory (`startNextHandDelay` / `nextHandWait` in `hands.ts`); an early deal gets 429 with `wait` (ms), and the page counts down on the New hand and Deal buttons. Finished hands are saved for the hand history (SRS-909.1): `recordRound()` in `app/api/blackjack/record.ts` closes the round's open `blackjack_hands` row with its first hand, inserting a row for a split's second hand with `bet_amount` (that hand's stake, doubled if it doubled), `result`, `net_amount`, `started_at`, `completed_at`, using only the table's existing columns; it runs before the payout, and if the row can't be closed nothing is paid (500) and the open row is refunded instead, so a round is never both paid and refunded. Nothing is written to `player_game_stats` yet, so blackjack's money won/lost stats (SRS-117/118) aren't recorded. Coins move only through `changeBalance()` there: an optimistic-lock read-then-conditional-update of `players.balance`, retried on a lost race (like the poker buy-in), refusing a debit for a non-`Active` account or above the balance.
- `GET /api/blackjack` returns the round in play (`{ hand }`) so a refresh resumes it. `POST /api/blackjack/deal` (`{ bet }`) refuses a second round, takes the bet, shuffles with `crypto.randomInt` and deals; a blackjack on the deal is paid at once, otherwise the round is kept. `POST /api/blackjack/action` (`{ handId, move, step }`) refuses the move if `step` no longer matches (a stale or double click), checks `canDouble()`/`canSplit()`, takes `moveCost()` first for Double and Split (refused, taking nothing, without enough coins), plays the move, and when the round ends removes it and credits `totalStake() + net` if positive, in one balance change. Deal and action each hold a per-player busy flag (`startBusy()`/`finishBusy()`) for their whole request, so two requests for one player never overlap. `GET /api/blackjack/history` returns the player's last 20 finished hands (`{ hands: BlackjackHistoryEntry[] }`, newest first). Routes share `requirePlayerId()` from `app/api/blackjack/auth.ts`.
- `app/blackjack/page.tsx` sends the bet and moves and draws the returned view: chips up to the balance (Undo/Clear), Deal, Hit/Stand/Double/Split (keys H/S/D/P; Double and Split show their cost and each has an `InfoTip` "i" button beside it that explains it on hover, focus, or tap without playing it, SRS-910.5/911.7). After a split both hands show side by side with their own total, bet, and result, the one being played highlighted; the felt shows the round's combined result. New hand keeps the same chips as the next bet. It calls `notifyBalanceChanged()` whenever coins move. Face-down cards show the player's equipped card back and every chip (the bet panel's buttons and the betting circle) its equipped chip set's skin for that value: `useEquippedLooks()` reads `GET /api/cosmetics` (again on `APPEARANCE_CHANGED_EVENT`) and a React context hands the two art keys to `PlayingCard` and `Chip`, which draw them with `CosmeticArt` (loaded with `next/dynamic`, like the nav bar); guests keep the table's own green card back and colored chips. Below the table, logged-in players see a Hand history list (time, bet, result, coins won or lost), reloaded when a round ends. The AI assistant panel is still a placeholder.

**Roulette (UR-301–305):**
- `lib/roulette/bets.ts` holds the SRS rules shared by the page and the API: the single-zero wheel order, pocket colors, bet types (`Number`, `Red`/`Black`, `Odd`/`Even`, `Low`/`High`, `Dozen1`–`3`, `Column1`–`3`), payouts (SRS-301.3/301.4), chip values, and the 500-coin limit.
- `app/roulette/page.tsx` keeps pending bets in the browser only — nothing is deducted until Spin (SRS-301.8), so Clear Bets never needs a refund. Spin sends `{ bets: [{ type, number?, amount }] }` to `POST /api/roulette/spin`; `components/roulette/RouletteWheel.tsx` spins to the returned number, and the result, per-bet outcomes, and balance (plus `notifyBalanceChanged()`) appear only when the wheel stops (SRS-304.2).
- `POST /api/roulette/spin` picks the winning number with `crypto.randomInt(37)` (never from the client) and calls `fn_spin_roulette(p_player_id, p_bets, p_winning_number)`, which in one transaction locks the player's row with `NOWAIT` (a second concurrent spin returns `busy`), validates the bets, deducts the stake, settles, credits, and writes `roulette_spins` + `roulette_bets` (SRS-302.2). Statuses map to 200 / 400 (`invalid_bets`, `over_limit`) / 409 (`insufficient_balance`, `busy`) / 403 / 404; an RPC error is a 500 and nothing is saved. Like the Daily Login Box function, only `service_role` may execute it.

**Cosmetics and blind boxes (UR-119, UR-120, UR-122 – UR-127):**
- The catalog lives in the database (`cosmetics`, seeded by `supabase/migrations/2026-10-22_cosmetics_and_blind_boxes.sql`, then `2026-10-22_holographic_items_and_new_boxes.sql` and `2026-10-23_holographic_outlines.sql`, and `schema.sql`): 3 Classic defaults plus 111 cosmetics in 13 blind boxes, 39 of them holographic (`cosmetics.is_holographic`: one card, one chip and one profile outline per box). `cosmetics.asset_path` is an art key; every cosmetic is drawn as SVG in code by `drawCosmetic(artKey, idPrefix, { avatar, value })` in `lib/cosmeticArt.ts` (no image files) and rendered by `components/cosmetics/CosmeticArt.tsx` (uses `useId()` so each drawing's gradient/filter ids are unique on the page). A test checks the seeded art keys and the drawings match exactly, so a new drawing needs its seed (and a new outline its `OUTLINE_ACCENTS` entry). Profile outlines are drawn in a 120×120 box around a radius-40 photo; `{ avatar: false }` draws only the ring, which `ProfilePhoto` overlays 28px past the photo on every side.
- Card backs are drawn with SVG lighting and noise filters (paper grain, raised designs via `embossLift`, which uses sRGB because linearRGB greys out dark colors) and fine line work. Holographic card backs use `holoCard()`, holographic chips `holoChip()` and holographic outlines `holoOutline()`; each holographic chip set has its own foil colors, edge-spot shape (`HOLO_EDGE`), body and center, and each holographic outline its box's foil colors and its own ornaments, so the sets don't look alike. All three have a CSS sweep of light that respects reduced motion (on outlines it's masked to the foil, so it never crosses the photo).
- Every chip is a set (`chipSet()`): `drawCosmetic(key, id)` is its main look (shop, profile), and `{ value }` with one of `CHIP_SKIN_VALUES` (5, 10, 25, 50, 100 — every chip value roulette and blackjack use) draws that value's skin: the value's own colors, the emblem, and the number on a small plate. A value keeps one color family on every chip (5 red, 10 blue, 25 green, 50 orange or purple, 100 black or gold) so it reads the same whichever chip is equipped. Blackjack draws the player's equipped card back and chip set (see Blackjack below); roulette (CL) doesn't draw equipped chips yet. `CosmeticArt` takes the same optional `value` to draw a chip's skin for one value.
- `lib/cosmetics.ts` (client-safe) holds the category list/order (SRS-119.3), `duplicateRefund()` (50% rounded up, SRS-126.3/126.4), `rewardChances(regular, holographic, chanceBp)` (each regular item's and each holographic item's chance as display strings, SRS-123.2/123.8/123.9), `HOLOGRAPHIC_ROLLS` (10,000) and `isBoxOnSale()` (SRS-122.3).
- Defaults: a trigger on `players` (`trg_players_grant_default_cosmetics`) gives every new account the 3 defaults, owned and equipped, in the same transaction (SRS-119.4, SRS-120.3); the migration back-filled existing players.
- `GET /api/cosmetics` returns the player's `owned` cosmetics (defaults first, then in the order won) and `equipped` (`{ Card, Chip, 'Profile Outline' }` → cosmetic id). `POST /api/cosmetics/equip` `{ cosmeticId }` checks ownership, then upserts `player_equipped_cosmetics` on `(player_id, category)` (SRS-120.4–120.6; the table's foreign keys also refuse unowned or wrong-category cosmetics). The profile's `CosmeticsSection` shows one row per category, equipped = green border; click an item, then Confirm, to equip.
- Blind boxes: `blind_boxes.available_from`/`available_until` (NULL = no limit, end time exclusive) make holiday boxes limited-time (SRS-122.3–122.5). Prices count regular items: 6 = 350 coins, 4 = 500, holiday ×1.25 = 625; Halloween/Thanksgiving/Christmas run Oct/Nov/Dec 2026, midnight to midnight Eastern, and the Spring, Summer, Autumn, Winter and Nature boxes are always on sale at 350. Holographic tier (SRS-123.8): `blind_boxes.holographic_chance_bp` (300 = 3%) is a box's combined chance of a holographic item, shared equally by its holographic items (card, chip and outline: 1% each); the regular items share the rest equally. `GET /api/shop/boxes` (anyone; a logged-in player also gets `owned` flags) lists boxes on sale, regular first, each with its rewards (regular items first, holographic last) and `chances: { regular, holographic }`. `POST /api/shop/buy` `{ boxId }` reads the box's chance and how many regular and holographic items it has, rolls `crypto.randomInt(10000)`, picks a uniform index into the group the roll lands in, and calls `fn_buy_blind_box(p_player_id, p_box_id, p_roll, p_pick)`, which in one transaction locks the player, checks Active / on sale / balance (SRS-124.5), makes the same holographic-or-regular choice from the roll, takes the item at that index in that group (ordered by `cosmetic_id`), stores it or refunds a duplicate, deducts the price and records the purchase (SRS-124.4, 125.1–125.6, 126.x). It returns `opened` (with `is_holographic`) `| insufficient_balance | unavailable | stale_pick | not_active | not_found`; `stale_pick` carries `regular_count`/`holographic_count` and the route draws again once. The 3-argument `fn_buy_blind_box(p_player_id, p_box_id, p_pick)` from before holographic items still exists, for copies of the app deployed before them: it draws only regular items. Only `service_role` can call either.
- `components/BlindBoxShop.tsx` shows each box (description, price, odds, refund, rewards in three columns (card backs, chips, outlines) with each holographic item at the bottom of its column, via `rewardRows()`, Owned badges and each item's chance, holographic items marked, a "Limited time · last day …" badge, SRS-123.9), asks for confirmation before buying (SRS-124.1–124.3), then `components/cosmetics/BlindBoxReveal.tsx` spins one reel (the `reel-spin` keyframes) to the won item and says new vs duplicate + refund (UR-127); a holographic win gets a rainbow frame and "Holographic!" once the reel stops (SRS-127.6). The profile's collection labels holographic items. The nav balance refreshes as soon as the purchase is saved, behind the reveal's backdrop, so a duplicate refund doesn't give the result away. Nothing is stored client-side, so a closed tab never replays a reveal (SRS-125.3, 127.5).

**Database changes:** `supabase/schema.sql` builds the whole database from scratch and starts by dropping every table, so never re-run it against the shared database. Each schema change also gets a script in `supabase/migrations/` that updates an existing database in place and is safe to re-run (e.g. `2026-10-12_daily_login_box.sql`); run it once in the Supabase SQL Editor.

**Poker (lobby, buy-in, full hands: blinds, cards, betting rounds, showdown):**
- `lib/pokerTable.ts` is a pure, DB-free `PokerTable` class: join an open seat — the one the player picked, or the first open one if none is given (with a chip stack supplied by the caller; `checkSeat()` lets the server reject a bad/taken seat before charging for it), leave a seat (returning the freed stack so the caller can refund it), enforce the seat cap, and hold the table's `bigBlind`/`smallBlind` (constructor args; `bigBlind` defaults to `DEFAULT_BIG_BLIND`, `smallBlind` to half of it rounded down; both exposed via `getState()`). `MIN_BUY_IN_MULTIPLIER`/`MAX_BUY_IN_MULTIPLIER` (50/200) live here too, shared by the server and the table page.
  It also runs each hand, with no clock of its own (the caller passes `now` and owns the timer): `phase` is `waiting` → `countdown` → `in-hand`. `updateCountdown(now)` (call after every join/leave and after a hand ends) starts a `HAND_START_COUNTDOWN_MS` (5 s, matching SRS-NFR-016) countdown once hand setup would deal in `MIN_PLAYERS_TO_START` (3) players (SRS-20.1/20.3; see missed blinds below — a 0-chip player sits out), or cancels it when it no longer would, and returns `'started' | 'cancelled' | null`. Straight after a hand the countdown is longer — `NEXT_HAND_DELAY_MS` (10 s after a showdown, 15 s after an all-in run-out, 6 s after everyone else folds; `finishHand()` sets it and the next `updateCountdown()` uses it once) — so players can see the result before the next deal; the server's start timer runs for the state's `countdownMsRemaining`. `startHand(randomIndex)` follows SRS-13/14: a random first button (SRS-13.1), afterwards the next seat clockwise holding a *clear* player (SRS-13.2; clockwise = increasing seat number), SB on the next clear player and BB on the next *eligible* one (SRS-14.1/14.2), every clear player plus the big blind plus accepted posters dealt in (SRS-13.4), the blinds moved from stacks into each blind seat's `bet` (a short stack posts all of it and is `allIn`), `currentBet` = big blind, and the turn (`activeSeat`) to the first player after the BB (SRS-18.1). Players then call `act(playerId, move, amount?)` with `fold | check | call | bet | raise`, where bet/raise `amount` is what the player's round contribution goes **to**. `getBettingOptions(seat, table)` (exported, and also used by the table page to draw its buttons) is the single source of what's legal: check only with nothing owed, call capped at the stack (SRS-15.7), bet/raise to between `currentBet + minRaise` (or the big blind when opening) and the whole stack, or all-in for less (SRS-15.3–15.6); `minRaise` becomes the size of each full raise (SRS-15.5), and an incomplete all-in raise sets `canRaise = false` for players who'd already acted since the last full raise (SRS-15.8). Out-of-turn or illegal actions are rejected with nothing changed and the allowed range in the error (SRS-3.1, 15.9/15.10). After each action a private `advance()` loop ends the hand if one player is left (SRS-18.6), otherwise ends the round when every able-to-act (in-hand, not all-in) player has acted and matched `currentBet` (SRS-18.3; blinds don't count as acting, so the BB gets its option) — returning any uncalled bet (SRS-19.5), collecting bets, burning a card and dealing the next street's community cards into `board` (SRS-17.1–17.6), and starting its round with the turn after the button (SRS-18.2/18.7/18.8) — or goes to showdown after the river, or, as soon as fewer than two players can still act, runs out the rest of the board with burns and no betting and then shows down (SRS-17.8/17.9/18.9); otherwise it passes the turn to the next able-to-act seat still owing an action (SRS-18.5). `pot`/`pots` only hold chips collected at the end of a round; chips bet this round stay in each `seat.bet`. `pots` is built from each seat's `totalBet` with a side pot per distinct all-in amount, each listing the in-hand seats eligible to win it (SRS-19.1–19.4). Cards: `startHand` shuffles a fresh deck with Fisher-Yates driven by `randomIndex` (SRS-16.1; `startHand`'s optional `presetDeck` replaces the shuffle in tests) and deals two hole cards each, one at a time in two passes from the small blind clockwise (SRS-16.2–16.4). Hole cards live in a private per-seat field that `getState()` strips (SRS-6.1); `getHoleCards()` hands them to the server to deliver privately. At showdown each in-hand player's best five of seven is ranked by `lib/pokerCards.ts` (SRS-5.1–5.5), each pot goes to the best hand among its eligible players, ties split in whole chips with odd chips one at a time clockwise from the button (SRS-5.6–5.8). A hand ending records `lastHandResult` — `fold` or `showdown`, the final `board`, `ranOut`, `shown` (each in-hand player's revealed cards and hand name, in SRS-6.5 order: the last bettor/raiser of the final round first, else the first player clockwise of the button; folded hands never, SRS-6.3), and `awards` with each winner's hand name — for the page to show until the next hand starts. Leaving: a player not in the hand (between hands, folded, or sat down mid-hand) is removed at once and refunded (a folded leaver's chips stay in the pot as dead money); a player still in the hand gets `{ ok, pending: true }`, is folded when the turn reaches them — immediately if it already has (SRS-21.2) — and removed when the hand ends (SRS-21.3), queued for the caller via `drainRemovals()`. A player who sits down mid-hand has `inHand: false` until they're dealt in. Once the last player has left (`leave()`, a busted timeout, or the end of a hand everyone asked to leave), the private `resetIfEmpty()` starts the table over: no `lastHandResult` or `lastAction` on show, no dealer button, no blind history (the hand count keeps going, since hole cards are sealed per hand number). The state's `countdownMsRemaining` is relative, like the Daily Login Box's `msRemaining`, so clients don't depend on their own clock. Turn timers (SRS-4) aren't built, so a player who never acts stalls the hand. Busted players (SRS-12): `isBustedSeat(seat)` (exported, also used by the table page) is seated with `chipStack === 0` and not `inHand` — an all-in player only counts once the hand ends (SRS-12.1). They're never dealt in (SRS-12.9) until `rebuy(playerId, chipStack)` gives them chips at the same seat (SRS-12.4/12.5; `checkRebuy()` lets the server refuse before charging, and a mid-hand buy-back plays from the next hand); `leave()` removes them as usual (SRS-12.3). If they do neither within `BUSTED_DECISION_TIMEOUT_MS` (60 s, SRS-NFR-015) they're removed (SRS-12.10), on the same no-clock-of-its-own pattern as the countdown: `trackBusted(now)` starts each newly busted seat's clock (kept in a private `bustedAt`) and stops it for anyone no longer busted, `nextBustedDeadline()` says when to fire, and `removeTimedOutBusted(now)` removes whoever is out of time (no chips, so nothing to refund). Each seat's state carries a relative `bustedMsRemaining` (null unless busted). Missed blinds (UR-011), all in the private `planHand()` / `startHand()`: *eligible* = seated with chips; *clear* = eligible with no missed-blind marker. At each successful hand start, every seated player not dealt in whose seat lies after the previous hand's big (small) blind seat, up to and including this hand's (kept in `previousBigBlindSeat`/`previousSmallBlindSeat`, since the public ones are cleared between hands), gets `missedBigBlind` (`missedSmallBlind`), both kept (SRS-11.1/11.2/11.4). New players owe nothing (SRS-11.3): `join()` after the first hand only sets a private `newcomer` flag, cleared at the next hand start. The button never lands on a newcomer (`canTakeButton()`, SRS-13.2); a newcomer it skips (SRS-11.13) (`newcomersInButtonPath()`, public as the seat's `waitingForButton`) sits that hand out and is dealt in free from the next, or elects to post (same `setPostMissedBlinds()`, always allowed for them) a live big blind plus a dead small blind to play it (SRS-11.14, offered by the page per SRS-11.16). `clearMissedBlinds()` also clears `newcomer` (SRS-11.15), so a skipped newcomer can't stall a waiting table. A marked player is dealt in when the big blind lands on them, posting it as usual (SRS-11.5), or after `setPostMissedBlinds(playerId, true)` (SRS-11.6): refused with no chips, owing nothing, or when — counted as clear — their seat would get the button or a blind next hand (SRS-11.9, `postingBlockedFor()`); re-checked at hand start and used for that hand only. A poster puts in a live big blind (in their `bet`, so they get the option) and a dead small blind (pushed to `deadContributions`, straight into the pot) (SRS-11.7/11.8). Being dealt in clears the markers (SRS-11.10). Whenever setup would come up short the table is waiting, and `clearMissedBlinds()` wipes every marker and election (SRS-11.11), checked by both `updateCountdown()` and `startHand()`. The table page shows an "SB" / "BB" / "SB+BB" marker at owing seats with "Waiting for BB" / "Posting next hand" on the name plate (SRS-11.12), and gives the owing player a panel to post (live BB + dead SB, its cost shown) or go back to waiting, sent as the `post-blinds` / `wait-for-big-blind` actions.
- `lib/pokerTables.ts` is the lobby's fixed list of six tables (`id`, `name`, `stakes` tier the lobby groups by, blinds, `maxSeats`): two each at 2/5, 5/10 and 10/20, all 6-max. Edit it to add/change tables; the server and both pages read it.
- `lib/pokerCards.ts` is pure: the `Card` type (rank then suit, e.g. `'As'`, `'Td'`), `createDeck()`, `shuffleDeck(deck, randomIndex)` (Fisher-Yates), and hand ranking — `scoreFive()` gives a comparable `[category, ...tiebreak ranks]` score (`compareScores()`), `evaluateHand()` picks the best five of five to seven cards and names it ("Full house, Kings over Fours", "Royal flush"). Aces play high or low in straights, no wraparounds, suits never rank (SRS-5.2–5.5). The table page uses it too, to name the player's own current hand.
- **The Realtime channels are public** — anyone with the anon key (which ships to every browser) can listen to and send on them — so neither session tokens nor hole cards go over them in the clear. `lib/pokerSecure.ts` (server-only, Node `crypto`, keyed by the `POKER_SERVER_SECRET` env var that the Next app and `npm run realtime` must share) handles both: `signRelayedAction()`/`verifyRelayedAction()` HMAC-sign a relayed action over a fixed field order (table, requestId, a fresh nonce, `issuedAt`, playerId, action fields), rejecting anything unsigned, tampered, for another table, or older than `RELAY_MAX_AGE_MS` (30 s); `sealHoleCards()`/`openHoleCards()` AES-256-GCM-encrypt a player's two cards under a key derived from the secret + table + hand number + player_id, so a sealed hand opens only for that player and that hand. Nothing is stored — matching `supabase/schema.sql`'s note that hole cards are never written anywhere.
- `POST /api/poker/action` (body `PokerActionRequest`: `{ tableId, requestId, action: 'join' | 'leave' | 'act' | 'rebuy', buyIn?, seatNumber?, move?, amount? }`, `Authorization: Bearer <token>`) resolves the token to a player_id, ignores anything the body claims about identity, signs the action, and broadcasts it on the table's channel via `channel.httpSend()` (REST, no subscription), returning 202. The outcome comes back as an `ack` on the channel. `POST /api/poker/hole-cards` (body `{ tableId, handNumber, sealed }`) opens the caller's sealed cards using the player_id from *their* token — someone else's sealed cards fail with 403.
- `lib/pokerRealtime.ts` holds the Supabase Realtime wire contract shared by the server and the client: one channel per table (`pokerTableChannelName(tableId)` → `poker:table-<id>`) plus the lobby channel `poker:lobby`, event names, `PokerSyncPayload` (`{ requestId, action: 'sync' }`, the only action a client sends on a channel directly), `PokerActionRequest`, `PokerAckPayload` (`{ requestId, ok, error?, seatNumber?, pending? }`), `PokerTableBroadcast` (the table `state` event: `TableState` plus `holeCards`, player_id → sealed cards), `PokerHoleCardsRequest`, and the lobby's `PokerLobbyState` (`{ tables: [{ tableId, name, smallBlind, bigBlind, maxSeats, seatedCount, phase, playerIds }] }`). There is no connection/session id in this contract — identity is always the signed player_id, never which connection sent a message.
- `server/pokerRealtimeServer.ts` wraps one in-memory `PokerTable` per entry in `lib/pokerTables.ts` (each with its own pre-hand countdown timer, `startTimer`: `refreshCountdown()` runs after every successful join/leave, and when the timer fires it calls `table.startHand()` with `crypto.randomInt` and broadcasts table + lobby) in a standalone Node process (`npm run realtime`, which refuses to start without `POKER_SERVER_SECRET`) that subscribes to every table's channel plus the lobby channel — no HTTP server, no port, since all traffic is an outbound connection to Supabase's hosted Realtime relay (this is what lets players on different laptops/networks join without any inbound port-forwarding). Unlike Next, this process doesn't auto-load env files, so it calls `dotenv`'s `config()` for `.env` and `.env.local` itself before reading `SUPABASE_*` and `POKER_SERVER_SECRET`. On a table's channel it answers an unsigned `sync` with the state, and otherwise handles only `action` events that pass `verifyRelayedAction()` and whose nonce it hasn't seen (`seenNonces`) — everything else is dropped without an ack. The signed player_id is the identity for `join`, `leave`, `act` and `rebuy`; `act` hands `move`/`amount` to `table.act()`, which does all the validation. The lobby channel only answers `sync`. Joining looks up the player's username via `getPlayerUsername()` (`lib/playerDisplay.ts`), rejects the join if the player is already seated at **any** table (one table at a time — a `joinsInFlight` set per player_id stops two quick joins at different tables from both passing that check during the awaits), validates `buyIn` is an integer in `[50, 200]` times that table's big blind and that the chosen `seatNumber` is open, then deducts it from `players.balance` via `deductBalance()` (an optimistic-lock read-then-conditional-update retried once on a lost race, since PostgREST calls can't share a transaction) before calling `table.join()` — if the seat join itself then fails (e.g. someone else took the seat in the gap), `refundBalance()` immediately gives the money back. `rebuy` (a busted player buying back in) uses the same `joinsInFlight` guard, checks `table.checkRebuy()`, validates `buyIn` against the same 50–200× big-blind range (SRS-12.6), deducts it via `deductBalance()` (which refuses more than the balance, SRS-12.7), then calls `table.rebuy()`, refunding if that fails; it then refreshes the countdown and broadcasts. Every `broadcastTable()` first runs `scheduleBustedTimeout()`, which calls `table.trackBusted()` and (re)sets the table's one `bustedTimer` for `nextBustedDeadline()`; when it fires it removes the timed-out players and broadcasts table and lobby (which schedules the next). Leaving calls `table.leave()` (looked up by the resolved `player_id`, regardless of which tab/connection is asking) and credits the returned chip stack back via `refundBalance()` before broadcasting — unless the ack is `pending` (still in the hand). After anything that can end a hand (`act`, `leave`, the start timer), `settleRemovals()` drains `table.drainRemovals()` and refunds each player removed at the hand's end, then `refreshCountdown()` starts the next hand's countdown. **A dropped connection does nothing** — there is no presence tracking and no disconnect handler, so closing the tab leaves the seat (and stack) exactly as it was; reopening the page shows the same seat via the next `state`/`sync`, and the explicit `leave` action works from that new tab because identity is the signed player_id, not a now-gone connection record. (Full disconnection-timeout removal, SRS-9.x/10.x, is still deferred.) `ack` broadcasts `{ requestId, ok, error?, seatNumber? }` are correlated by `requestId` (Realtime broadcast has no request/reply primitive, so this emulates one); `state` (full `table.getState()`, including each seat's `chipStack`, plus `holeCards` — each dealt-in player's cards sealed with `sealHoleCards()` on every broadcast; the hand starts from the timer use `crypto.randomInt` for both the first button and the shuffle) is broadcast on the table's channel after every successful join/leave and on-demand via a `sync` action for late-joining clients; each join/leave also re-broadcasts the lobby's `state` on `poker:lobby`. Seats carry only a username, never a profile photo: Realtime broadcast has a payload size limit a multi-MB photo can blow past, which silently drops the whole `state` message for everyone — see `GET /api/players/[playerId]/avatar` below.
- `app/poker/usePoker.ts` holds the client hooks both poker pages share: `usePlayerProfile()` (reads `player_token`, loads `GET /api/profile`, which already returns `balance`) and `usePokerChannel(channelName, enabled, onState)`, which subscribes via `getSupabaseBrowserClient()` (`lib/supabase.ts`, a module-level singleton — `createClient()` isn't memoized by Supabase itself, and React Strict Mode's double-invoked effects in dev would otherwise spin up multiple concurrent Realtime sockets), sends `sync` once subscribed, and returns `sendAction(token, request)`, which POSTs to `/api/poker/action` (registering for the ack first, so a fast one can't be missed) and resolves with the matching `ack` from the channel — or an error if the POST fails or no ack arrives within 10 s (e.g. `npm run realtime` isn't running).
- `app/poker/page.tsx` is the lobby (what the home page's Poker button opens). Behind the same "must be logged in" gate as `app/profile/page.tsx`, it subscribes to `poker:lobby` and shows every table, grouped by stakes tier, as a card with a mini table whose seat dots fill in with the live `seatedCount`, plus its blinds, buy-in range and `phase` ("Starting soon" / "In play"), with a Join link to `/poker/[tableId]` (disabled when full). If the lobby state shows the player already seated somewhere (their id in a table's `playerIds`), it `router.replace`s them straight to that table instead.
- `app/poker/[tableId]/page.tsx` is one table (an unknown `tableId` shows a link back to the lobby). Layout: on a laptop or desktop (`useMediaQuery('(min-width: 1024px) and (min-height: 600px)')`) the page is exactly the window's height — a slim top bar (lobby link, table name, stakes, blinds, buy-in, status pills), then a row of three: a left panel (you: photo, balance, stack and Leave, then your hole cards and hand name), the table, and a right panel (what you can do) — and the table is sized from the measured room between the panels (`tableAreaRef`; 1.9 times as wide as tall when there's room, rounder down to 1.4 when width runs short, leaving space for the seats that overhang its edge, at most 700px tall). On a phone the three stack: the table, your actions, then you. Seats scale up with a big table (the CSS `scale` property, up to 1.3×) and a table 900px+ wide gets `lg` board cards (`BOARD_CARD_PITCH` keeps the deck flights lined up). The right panel holds the buy-in form, the busted or owed-blinds panels, or `BettingControls` (Fold and Check/Call side by side, then the amount with its slider and shortcuts, then Bet/Raise), stacked to fit the panel. Narrower screens keep a fixed-size table and scroll. It subscribes to that table's channel and sends `join`/`leave`/`act`/`rebuy` through `sendAction()` with the player's `player_token` — never a free-typed username, and never on the channel itself. Once per hand it posts its own sealed entry from `state.holeCards` to `/api/poker/hole-cards` and shows the opened cards face up on its seat and large in the controls panel with the current hand's name; other in-hand seats show two card backs. The felt shows the board (five slots) during a hand; between hands it keeps the last hand's board, result line, and each revealed hand (cards plus hand name at the seat, winners' cards ringed) until the next deal. An unseated player clicks an open seat to pick it, then sees a buy-in input clamped client-side to `[50, min(200, balance / bigBlind)] × bigBlind` (the server re-validates this regardless) once the table's `bigBlind` is known from its first `table:state`; the pick is cleared if someone else sits there first. Each seat shows its occupant's chip stack once seated, and a player's own stack is shown next to their Leave button. The felt's center shows "Waiting for players · N/3" (SRS-20.5), then the countdown (rebuilt locally from `countdownMsRemaining` on every `state` and ticked every 250 ms), then the hand number, pot and amount to call; the dealer button (SRS-13.5) and each seat's posted `bet` (labelled SB/BB) sit between the seat and the pot, and a player who sat down mid-hand is dimmed with "Next hand". After a successful join, the page refetches its own balance and calls `notifyBalanceChanged()` (`lib/balanceEvents.ts`), since joining doesn't navigate; after a successful leave it sends the player back to the lobby (`/poker`) — or, for a `pending` leave mid-hand, shows "Leaving after this hand" and navigates once its seat disappears from the state. During a hand the active seat pulses with a "To act" tag (SRS-3.2), seats show their latest action, Folded, or All-in, the felt shows the street, pot, side pots and current bet, and between hands it shows the last hand's result over the countdown. When the player is busted, the controls panel replaces their stack and Leave button with "You're out of chips": the same buy-in amount fields as joining (shared as `buyInFields`, reset to the minimum and with the balance refreshed when they go bust) plus **Buy back in** and **Leave table** (SRS-12.2), or, if their balance can't cover the minimum, a shop link and Leave table; a refused buy-back shows the server's reason (SRS-12.8). The panel counts down "Choose within Ns" from the seat's `bustedMsRemaining` (rebuilt locally like the pre-hand countdown). If the seat then disappears while busted without the player clicking Leave, the page knows the server removed them and says so above the join form until they sit down again (SRS-9.11). On the player's turn the controls panel renders `app/poker/BettingControls.tsx`: Fold, Check/Call, and Bet/Raise with an amount field, slider and Min / ½ Pot / Pot / All-in shortcuts, all bounded by `getBettingOptions()`; it's re-keyed on every turn so the amount resets. Animations (keyframes and `poker-*` classes at the end of `app/globals.css`, all switched off under `prefers-reduced-motion`): a deck sits left of the board and a muck pile right of it (`app/poker/tableAnimations.tsx`: `DeckStack`, `MuckPile`, and `tableGeometry()` from the table's measured size, since the flights are pixel transforms; on a table narrower than 560px both stay hidden in the middle). At each new hand the last hand's cards fly into the deck and it riffle-shuffles twice (`SHUFFLE_MS`), then hole cards fly from the deck to each seat in deal order (this player's own arrive face up), board cards (`SlamCard`) leave the deck face down, rise, flip over in a white glare and slam onto the felt — the flop one after another, the turn harder, the river hardest — each landing setting off an `ImpactBurst` (shockwave ring, sparks, dust; gold for the river) and shaking the whole table (`poker-quake-a/-b` on the table container, alternated so a shake restarts; strength per street), with a flash across the felt for the river, bets slide out from the seat, the pot pulses when it grows, folded hands — this player's own too — are thrown onto the muck pile, which grows by two cards per fold and stays until the next hand gathers it, showdown hands slam down the same way, one hand after another in reveal order (winners with a gold burst and a harder shake), an all-in run-out (`lastHandResult.ranOut`) is played out in the result view after the reveals, street by street from however much of the board was out before (`boardSeenRef`), and only then do chips slide from the pot to each winner (each hand's name on its seat, and the winners' lines, wait until then so nothing gives the run-out away). Nothing replays on opening the page: `loadedRef` records what was on the table then, and a hand already in progress is drawn as it stands (no shuffle, deal, board slams or mucking), and a result already on show gets no timeline, so no reveals, run-out or payout. Cards brought out by a brand-new action wait for its callout to pass (`calloutWait` = `calloutDuration()` of an action whose id the page hasn't seen yet, passed as the `wait` of `boardSlam()` / `boardHits()` / `showdownTimeline()`), so a "CALL!" doesn't hide the flop or a "FOLD…" the payout; `SlamCard` freezes its timing when it first appears. One `showdownTimeline()` / `boardSlam()` timeline in `app/poker/tableAnimations.tsx` drives both the CSS delays and the scheduled shakes (`scheduleHits()`), and is unit-tested in `__tests__/lib/tableAnimations.test.ts`. Between hands chips slide from the pot to each winner, then a "+amount" rises over the winner's glowing seat while the result (each winner's amount and hand) shows in the middle. Every action also gets a comic "OBJECTION!"-style callout across the table (`app/poker/ActionCallout.tsx`, `callout-*` keyframes in `app/globals.css`): a jagged speech bubble with slanted outlined lettering whose shape, colours and motion scale with the move — Fold sags and drops, Check taps, Call glides, Bet punches in, Raise slams in shaking with speed lines, All-in also flashes the table. It plays once per new `lastAction.id` (an engine counter, so a re-broadcast doesn't replay it) and skips the action already on the table when the page loads. Each animated element is keyed on what it shows (hand number, street, bet, card state), so a change remounts it and replays the animation; directions come from CSS variables set per seat (`cssVars()`). As seats appear in `table:state`, the page separately fetches each occupant's avatar via `GET /api/players/[playerId]/avatar` and caches it client-side by `player_id`, rendering it once it arrives (or an initial-letter fallback until then / if there is none), matching SRS-8.1/8.2. Alongside it, the page fetches each occupant's equipped cosmetics from `GET /api/players/[playerId]/cosmetics` (public, `{ card, chip, outline }` art keys, null for an empty slot) and shows them off: their card back on their face-down cards, their chip on their bet and stack, and their profile outline around their seat photo (via `PlayingCard`'s `backArtKey`, `PlayerChip` and `ProfileOutline` in `app/poker/pokerUi.tsx`, which lazy-load `CosmeticArt`). Until that arrives, a seat keeps the plain red card backs and the table's stakes chip.
- **Emotes** (Clash Royale style): `lib/emotes.ts` lists them (`EMOTES`, each with `isDefault`; for now every one is a default every player has — box-won emotes will be added with `isDefault: false` and an ownership check in `canSendEmote()`), with the cooldown (`EMOTE_COOLDOWN_MS`, 2.5 s) and how long one shows (`EMOTE_SHOW_MS`, 2.6 s). The art is Chip, a poker-chip mascot pulling a face, drawn as SVG per emote id in `components/emotes/EmoteArt.tsx`. A seated player's round button at the table's bottom-left (`app/poker/EmotePicker.tsx`) opens the grid at any time; sending is an `emote` action through `POST /api/poker/action` (the emote id is part of the signature), and the poker server checks the sender is seated, owns the emote and is off cooldown, then sends a separate `emote` broadcast (`POKER_EVENT_EMOTE`, `PokerEmotePayload` with a counting `id`) — not part of the table state. The page (`usePokerChannel`'s `onEmote`) shows it over that seat for `EMOTE_SHOW_MS`: it pops up (`emote-pop`) and does its own move (`emote-move-<id>`, keyframes in `app/globals.css`).
- `GET /api/players/[playerId]/avatar` returns `{ avatarUrl }` for any player_id, unauthenticated — a seated player's avatar is public to anyone viewing the table, the same as their username (SRS-8.1). This is how the poker page gets avatars now that they're no longer carried through the Realtime broadcast. Unlike `GET /api/profile`, it returns a resized 96×96 thumbnail (via `photoToAvatarDataUrl()`), not the original upload (up to 5MB, SRS-115.3) — seat avatars render under 100px, and serving the full image made the table slow to populate over a bandwidth-limited link (e.g. an ngrok tunnel for cross-network testing).
- `lib/playerDisplay.ts` holds `photoToDataUrl()` (bytea → full-size `data:image/png;base64,...`, used by `GET /api/profile`), `photoToAvatarDataUrl()` (bytea → a 96×96 thumbnail via `sharp`, used only by the avatar route above), `getPlayerDisplay()` (username + full photo, used by `app/api/profile/route.ts`), and `getPlayerUsername()` (username only, used by the poker realtime server's join handler so it never pulls the photo column into a hot path).

**Tests (`__tests__/`):**
- Vitest with `environment: 'node'`.
- `lib/supabase` is mocked via `vi.mock` in the API route tests; `lib/auth.ts` is left unmocked so real bcrypt hashing/verification and session-token hashing are exercised. Tests import route handler functions directly and call them with `new Request(...)`.
- The Supabase mock in each test file is a small fake query builder (per-table, chainable, thenable) rather than a single fixed response — see the comment at the top of `__tests__/api/auth.test.ts` for the shape, since several routes chain `.select()/.eq()/.ilike()/.maybeSingle()` or await an `.insert()/.update()/.upsert()` directly without `.select()`.
- `lib/pokerTable.ts`, `lib/pokerTables.ts`, `lib/pokerCards.ts` and `lib/pokerSecure.ts` are pure (or Node-crypto only) and unit-tested directly with no mocking (hands — setup, dealing, betting, rounds, side pots, showdowns, leaving mid-hand — in `__tests__/lib/pokerTableHand.test.ts`, passing a fixed `randomIndex`, explicit `now`, and a `stackDeck()`-built preset deck so the cards are known; its `play()` helper runs a list of `[seat, move, amount?]` actions and fails on the first rejected one). `__tests__/api/poker.test.ts` covers the two poker API routes with a mocked Supabase client whose `channel().httpSend` records what would be broadcast.
- Tests live in `__tests__/` and are matched by the glob `__tests__/**/*.test.ts`.
