# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # install dependencies
npm run dev        # start dev server (http://localhost:3000)
npm run realtime   # start the poker realtime relay process (connects to Supabase Realtime), separate process
npm run build      # production build
npm test           # run all tests (vitest)
npx vitest run __tests__/api/auth.test.ts   # run a single test file
```

## Environment setup

Copy `.env.example` to `.env.local` and fill in your Supabase credentials before running the app. `SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are read by `lib/supabase.ts` — either URL prefix works. Use the service-role key, not the anon key: none of the tables below have Row Level Security policies, and the auth routes read `players.password_hash` directly, so the anon key must not be relied on to protect that data. The browser, however, needs its own `NEXT_PUBLIC_SUPABASE_ANON_KEY` (distinct from the server-only `SUPABASE_ANON_KEY`) for the poker page's Realtime connection — only `NEXT_PUBLIC_`-prefixed vars reach the client bundle, and the anon key (never the service-role key) is the one meant to be shipped there. The poker room also needs `POKER_SERVER_SECRET` (any long random string, the same for the Next app and `npm run realtime`, never `NEXT_PUBLIC_`): it signs relayed poker actions and seals hole cards (`lib/pokerSecure.ts`).

## Architecture

This is a Next.js 14 App Router project with Tailwind CSS, backed directly by the Postgres schema in `supabase/schema.sql` (no Supabase Auth — see below). The poker room additionally runs its own Node process (`server/pokerRealtimeServer.ts`) that relays table state through a Supabase Realtime channel (Broadcast + Presence), separate from Next's HTTP server, matching `docs/architecture/C2.mmd`.

**Auth and profile data model:**
The schema (`supabase/schema.sql`) has no email column and no link to Supabase's built-in `auth.users` — it is entirely username/password based:
- `players` — one row per account: `player_id`, `first_name`, `last_name`, `birthday`, `password_hash`, `balance`, `bio`, `profile_photo` (BYTEA, PNG only), `account_status`.
- `usernames` — a player's username lives here, not as a column on `players`, so that a changed username can stay reserved for 24 hours (`is_current` / `reserved_until`).
- `player_sessions` — one row per player (`player_id` is UNIQUE), holding a hash of that player's current session token; a new login overwrites it, which is how a second login invalidates the first.

**Request flow for auth:**
1. `app/register/page.tsx` and `app/login/page.tsx` are `'use client'` forms that POST to the API routes via `fetch`.
2. `app/api/auth/register/route.ts` validates the SRS-101/102 field rules (names, username shape, password shape, minimum age — see `lib/auth.ts`), hashes the password with bcrypt, inserts into `players`, then inserts the username into `usernames`. If the username insert fails (lost a uniqueness race), the route deletes the just-created `players` row by hand, since two separate PostgREST calls can't share a transaction.
3. `app/api/auth/login/route.ts` looks up the current username (case-insensitively) in `usernames`, verifies the password against `players.password_hash` with bcrypt, rejects a `Pending Deletion` account, then generates a random session token, stores its SHA-256 hash in `player_sessions` (upsert on `player_id`, so logging in elsewhere invalidates the old session), and returns the raw token to the client.
4. The client stores that token in `localStorage` under `player_token` and sends it as `Authorization: Bearer <token>` on `/api/profile`, `/api/profile/avatar`, and `/api/profile/balance`. Those routes resolve it back to a `player_id` via `getPlayerIdForToken()` in `lib/auth.ts`, which hashes the token and looks it up in `player_sessions`. `POST /api/auth/logout` (the profile page's Log out button, SRS-105.1) deletes the `player_sessions` row matching the token's hash, and the client then clears `player_token`.
5. `lib/supabase.ts` — `getSupabaseClient()` returns `null` when env vars are missing; every route guards against this and returns a 500. Its client passes `cache: 'no-store'` on every fetch: Next 14 otherwise keeps server-side `fetch()` results (i.e. every supabase-js query) in its Data Cache, so a route Next treats as static — one that never reads the request, like `GET /api/players/[playerId]/avatar` — would serve its first query result forever.

**Profile:**
- `GET`/`PATCH /api/profile` read and update `players` + the current row in `usernames`. There is no "create profile" step — registration already creates the full `players` row, so `PATCH` only edits `bio` for now (SRS-114.1/114.2: optional, 50 words max, empty stored as `NULL`). Word counting lives in `lib/bio.ts` (`countBioWords`, `BIO_MAX_WORDS`), shared by the API and the bio editor so their counts always match (SRS-114.5).
- `app/profile/page.tsx` lays out: the photo (`components/profile/ProfilePhoto.tsx`) with Log out underneath; first/last name, then username and password (dots only — only the hash exists, SRS-104.5) as boxes from `components/profile/ProfileField.tsx`; the bio; then `CosmeticsSection` and `StatsSection`. A field with a pencil opens a pop-up built on `components/profile/EditDialog.tsx` (Cancel/Escape discard, Save replaces and closes); the bio's is `BioEditor.tsx`, with a live "N / 50 words" count that turns red and disables Save past the limit. Names, username, and password get pencils as their editing is built. `CosmeticsSection` (defaults only, equipped = green border) and `StatsSection` ("Money won/lost" / "Time played" tabs, totals then per game, dashes until games record results) are placeholders until those features exist.
- Clicking the photo opens a small menu: Upload new photo (which also replaces an existing one, SRS-115.4) and, only when there is a photo, a red Remove photo (SRS-115.6); upload/remove errors show inside the menu, and a click outside or Escape closes it. With no photo it shows `components/profile/DefaultAvatar.tsx`, a blank person icon (SRS-115.5) meant to be reused wherever a player's own photo is shown (the poker seats still use their own initial-letter fallback).
- `POST /api/profile/avatar` validates the upload is a PNG by file signature (not filename) and ≤5MB (SRS-115.1–115.3), then writes it straight into `players.profile_photo` as a Postgres hex-encoded bytea string; `DELETE /api/profile/avatar` sets that column back to `NULL` (no DB change was needed — `NULL` already means the default icon). Both routes and `GET /api/profile` convert that column to a `data:image/png;base64,...` URL for the client — there is no Supabase Storage bucket.

**Home page and nav bar:**
- `lib/games.ts` is the single list of games on the home page (SRS-107.1), each with a `tag` shown over its picture. A game with `href: null` is dimmed with "Coming soon"; setting `href` to the game's route makes it playable, and its links send guests to `/login` instead (SRS-108.3, via `playHref()` in `components/useSignedIn.ts`, which also holds the `useSignedIn()` hook that reads `player_token`).
- The home page (`app/page.tsx`) treats every game equally — no game is featured. Top to bottom: `components/HomeHero.tsx` (heading, plus signup/login buttons for guests or "Start playing" / "Claim free coins" for signed-in players), `components/GameGrid.tsx` (one card per game, the whole card a link), and a Daily Login Box promo linking to `/shop` (its coin range comes from `DAILY_LOGIN_BOX_REWARDS`). All pictures are inline SVG in `components/GameArt.tsx` — one per game, keyed by the game's `id` (a new game needs an entry in its `ART` map, or it gets a plain placeholder), plus `HeroArt`. There are no image files.
- `components/NavBar.tsx` is rendered on every page by `app/layout.tsx`: Home and a cart (linking to `/shop`) on the left, the balance and a profile icon on the right. It re-reads `player_token` on every navigation and fetches `GET /api/profile/balance`, which returns only `{ balance }` because the full profile's photo can be several MB. Guests see 0 coins (SRS-109.4) and the profile icon links to `/login`; a 401 clears the stale token.
- A page that changes the balance without navigating should call `notifyBalanceChanged()` (`lib/balanceEvents.ts`) afterwards; the nav bar listens for that event and refetches immediately (SRS-110.5, SRS-NFR-104).
- The nav bar is `h-14`, so pages use `min-h-page` (defined in `tailwind.config.js` as the window height minus 3.5rem) instead of `min-h-screen`.

**Cosmetic shop — Daily Login Box (UR-128):**
- `app/shop/page.tsx` shows the Daily Login Box first (`components/DailyLoginBox.tsx`), then a "Blind boxes — coming soon" placeholder (UR-122–127 aren't built).
- `GET /api/daily-login-box` returns `{ available, nextAvailableAt, msRemaining }` for the logged-in player, from their latest `daily_login_box_claims` row; a player with no rows can open a box right away (SRS-110.2). `msRemaining` is computed server-side so the countdown doesn't depend on the browser's clock.
- `POST /api/daily-login-box` picks the reward with `crypto.randomInt` via `pickDailyLoginBoxReward()` (`lib/dailyLoginBox.ts`: 25/50/75/100 coins at 40/30/20/10%), then calls the Postgres function `fn_open_daily_login_box(p_player_id, p_reward)` through `supabase.rpc`. That function does everything that must succeed or fail together (SRS-128.9) in one transaction: it locks the player's row (so simultaneous requests can't both claim, SRS-128.19), rejects non-`Active` accounts and claims inside the 24-hour cooldown, credits the balance, and inserts the claim with `next_available_at = claimed_at + 24 hours`. It returns `{ status: 'opened' | 'cooldown' | 'not_active' | 'not_found', ... }`, which the route maps to 200/409/403/404; an RPC error maps to 500 and nothing is saved (SRS-128.21).
- `fn_open_daily_login_box` has its `EXECUTE` grant revoked from `anon`/`authenticated` (only `service_role` can call it), because the anon key is public.
- The box's button says **Spin**. After the API reply (i.e. after the transaction has committed), `components/SlotReveal.tsx` pops up three slot reels that stop left to right on the reward (last one at 1.5 s), followed 250 ms later by the "+N coins" result (SRS-128.10). The reels use the `reel-spin` CSS keyframes in `app/globals.css`, which are timed by the clock rather than by redraws; the last reel's `animationend` (with a backup timer) marks the stop. So the reveal doesn't spoil itself, the nav bar's balance is refreshed via `onStopped` when the reels stop, not when the API replies, which is still inside SRS-NFR-104's 2 seconds. The card also leaves the won amount unhighlighted until the pop-up closes. The page always rebuilds its state from `GET`, so a refresh mid-spin shows the cooldown instead of replaying the reveal (SRS-128.16/128.17).

**Roulette (UR-301–305):**
- `lib/roulette/bets.ts` holds the SRS rules shared by the page and the API: the single-zero wheel order, pocket colors, bet types (`Number`, `Red`/`Black`, `Odd`/`Even`, `Low`/`High`, `Dozen1`–`3`, `Column1`–`3`), payouts (SRS-301.3/301.4), chip values, and the 500-coin limit.
- `app/roulette/page.tsx` keeps pending bets in the browser only — nothing is deducted until Spin (SRS-301.8), so Clear Bets never needs a refund. Spin sends `{ bets: [{ type, number?, amount }] }` to `POST /api/roulette/spin`; `components/roulette/RouletteWheel.tsx` spins to the returned number, and the result, per-bet outcomes, and balance (plus `notifyBalanceChanged()`) appear only when the wheel stops (SRS-304.2).
- `POST /api/roulette/spin` picks the winning number with `crypto.randomInt(37)` (never from the client) and calls `fn_spin_roulette(p_player_id, p_bets, p_winning_number)`, which in one transaction locks the player's row with `NOWAIT` (a second concurrent spin returns `busy`), validates the bets, deducts the stake, settles, credits, and writes `roulette_spins` + `roulette_bets` (SRS-302.2). Statuses map to 200 / 400 (`invalid_bets`, `over_limit`) / 409 (`insufficient_balance`, `busy`) / 403 / 404; an RPC error is a 500 and nothing is saved. Like the Daily Login Box function, only `service_role` may execute it.

**Database changes:** `supabase/schema.sql` builds the whole database from scratch and starts by dropping every table, so never re-run it against the shared database. Each schema change also gets a script in `supabase/migrations/` that updates an existing database in place and is safe to re-run (e.g. `2026-10-12_daily_login_box.sql`); run it once in the Supabase SQL Editor.

**Poker (lobby, buy-in, full hands: blinds, cards, betting rounds, showdown):**
- `lib/pokerTable.ts` is a pure, DB-free `PokerTable` class: join an open seat — the one the player picked, or the first open one if none is given (with a chip stack supplied by the caller; `checkSeat()` lets the server reject a bad/taken seat before charging for it), leave a seat (returning the freed stack so the caller can refund it), enforce the seat cap, and hold the table's `bigBlind`/`smallBlind` (constructor args; `bigBlind` defaults to `DEFAULT_BIG_BLIND`, `smallBlind` to half of it rounded down; both exposed via `getState()`). `MIN_BUY_IN_MULTIPLIER`/`MAX_BUY_IN_MULTIPLIER` (50/200) live here too, shared by the server and the table page.
  It also runs each hand, with no clock of its own (the caller passes `now` and owns the timer): `phase` is `waiting` → `countdown` → `in-hand`. `updateCountdown(now)` (call after every join/leave and after a hand ends) starts a `HAND_START_COUNTDOWN_MS` (5 s, matching SRS-NFR-016) countdown once `MIN_PLAYERS_TO_START` (3) are seated **with chips** (a 0-chip player sits out; SRS-12 busted handling isn't built), or cancels it if the count drops below that, and returns `'started' | 'cancelled' | null`. `startHand(randomIndex)` follows SRS-13/14: a random first button (SRS-13.1), afterwards the next seat with chips clockwise (SRS-13.2; clockwise = increasing seat number), SB/BB on the next ones, every seated player with chips dealt in (missed blinds, SRS-11, aren't tracked), the blinds moved from stacks into each blind seat's `bet` (a short stack posts all of it and is `allIn`), `currentBet` = big blind, and the turn (`activeSeat`) to the first player after the BB (SRS-18.1). Players then call `act(playerId, move, amount?)` with `fold | check | call | bet | raise`, where bet/raise `amount` is what the player's round contribution goes **to**. `getBettingOptions(seat, table)` (exported, and also used by the table page to draw its buttons) is the single source of what's legal: check only with nothing owed, call capped at the stack (SRS-15.7), bet/raise to between `currentBet + minRaise` (or the big blind when opening) and the whole stack, or all-in for less (SRS-15.3–15.6); `minRaise` becomes the size of each full raise (SRS-15.5), and an incomplete all-in raise sets `canRaise = false` for players who'd already acted since the last full raise (SRS-15.8). Out-of-turn or illegal actions are rejected with nothing changed and the allowed range in the error (SRS-3.1, 15.9/15.10). After each action a private `advance()` loop ends the hand if one player is left (SRS-18.6), otherwise ends the round when every able-to-act (in-hand, not all-in) player has acted and matched `currentBet` (SRS-18.3; blinds don't count as acting, so the BB gets its option) — returning any uncalled bet (SRS-19.5), collecting bets, burning a card and dealing the next street's community cards into `board` (SRS-17.1–17.6), and starting its round with the turn after the button (SRS-18.2/18.7/18.8) — or goes to showdown after the river, or, as soon as fewer than two players can still act, runs out the rest of the board with burns and no betting and then shows down (SRS-17.8/17.9/18.9); otherwise it passes the turn to the next able-to-act seat still owing an action (SRS-18.5). `pot`/`pots` only hold chips collected at the end of a round; chips bet this round stay in each `seat.bet`. `pots` is built from each seat's `totalBet` with a side pot per distinct all-in amount, each listing the in-hand seats eligible to win it (SRS-19.1–19.4). Cards: `startHand` shuffles a fresh deck with Fisher-Yates driven by `randomIndex` (SRS-16.1; `startHand`'s optional `presetDeck` replaces the shuffle in tests) and deals two hole cards each, one at a time in two passes from the small blind clockwise (SRS-16.2–16.4). Hole cards live in a private per-seat field that `getState()` strips (SRS-6.1); `getHoleCards()` hands them to the server to deliver privately. At showdown each in-hand player's best five of seven is ranked by `lib/pokerCards.ts` (SRS-5.1–5.5), each pot goes to the best hand among its eligible players, ties split in whole chips with odd chips one at a time clockwise from the button (SRS-5.6–5.8). A hand ending records `lastHandResult` — `fold` or `showdown`, the final `board`, `ranOut`, `shown` (each in-hand player's revealed cards and hand name, in SRS-6.5 order: the last bettor/raiser of the final round first, else the first player clockwise of the button; folded hands never, SRS-6.3), and `awards` with each winner's hand name — for the page to show until the next hand starts. Leaving: a player not in the hand (between hands, folded, or sat down mid-hand) is removed at once and refunded (a folded leaver's chips stay in the pot as dead money); a player still in the hand gets `{ ok, pending: true }`, is folded when the turn reaches them — immediately if it already has (SRS-21.2) — and removed when the hand ends (SRS-21.3), queued for the caller via `drainRemovals()`. A player who sits down mid-hand has `inHand: false` until the next one. The state's `countdownMsRemaining` is relative, like the Daily Login Box's `msRemaining`, so clients don't depend on their own clock. Turn timers (SRS-4) aren't built, so a player who never acts stalls the hand.
- `lib/pokerTables.ts` is the lobby's fixed list of six tables (`id`, `name`, `stakes` tier the lobby groups by, blinds, `maxSeats`): two each at 2/5, 5/10 and 10/20, all 6-max. Edit it to add/change tables; the server and both pages read it.
- `lib/pokerCards.ts` is pure: the `Card` type (rank then suit, e.g. `'As'`, `'Td'`), `createDeck()`, `shuffleDeck(deck, randomIndex)` (Fisher-Yates), and hand ranking — `scoreFive()` gives a comparable `[category, ...tiebreak ranks]` score (`compareScores()`), `evaluateHand()` picks the best five of five to seven cards and names it ("Full house, Kings over Fours", "Royal flush"). Aces play high or low in straights, no wraparounds, suits never rank (SRS-5.2–5.5). The table page uses it too, to name the player's own current hand.
- **The Realtime channels are public** — anyone with the anon key (which ships to every browser) can listen to and send on them — so neither session tokens nor hole cards go over them in the clear. `lib/pokerSecure.ts` (server-only, Node `crypto`, keyed by the `POKER_SERVER_SECRET` env var that the Next app and `npm run realtime` must share) handles both: `signRelayedAction()`/`verifyRelayedAction()` HMAC-sign a relayed action over a fixed field order (table, requestId, a fresh nonce, `issuedAt`, playerId, action fields), rejecting anything unsigned, tampered, for another table, or older than `RELAY_MAX_AGE_MS` (30 s); `sealHoleCards()`/`openHoleCards()` AES-256-GCM-encrypt a player's two cards under a key derived from the secret + table + hand number + player_id, so a sealed hand opens only for that player and that hand. Nothing is stored — matching `supabase/schema.sql`'s note that hole cards are never written anywhere.
- `POST /api/poker/action` (body `PokerActionRequest`: `{ tableId, requestId, action: 'join' | 'leave' | 'act', buyIn?, seatNumber?, move?, amount? }`, `Authorization: Bearer <token>`) resolves the token to a player_id, ignores anything the body claims about identity, signs the action, and broadcasts it on the table's channel via `channel.httpSend()` (REST, no subscription), returning 202. The outcome comes back as an `ack` on the channel. `POST /api/poker/hole-cards` (body `{ tableId, handNumber, sealed }`) opens the caller's sealed cards using the player_id from *their* token — someone else's sealed cards fail with 403.
- `lib/pokerRealtime.ts` holds the Supabase Realtime wire contract shared by the server and the client: one channel per table (`pokerTableChannelName(tableId)` → `poker:table-<id>`) plus the lobby channel `poker:lobby`, event names, `PokerSyncPayload` (`{ requestId, action: 'sync' }`, the only action a client sends on a channel directly), `PokerActionRequest`, `PokerAckPayload` (`{ requestId, ok, error?, seatNumber?, pending? }`), `PokerTableBroadcast` (the table `state` event: `TableState` plus `holeCards`, player_id → sealed cards), `PokerHoleCardsRequest`, and the lobby's `PokerLobbyState` (`{ tables: [{ tableId, name, smallBlind, bigBlind, maxSeats, seatedCount, phase, playerIds }] }`). There is no connection/session id in this contract — identity is always the signed player_id, never which connection sent a message.
- `server/pokerRealtimeServer.ts` wraps one in-memory `PokerTable` per entry in `lib/pokerTables.ts` (each with its own pre-hand countdown timer, `startTimer`: `refreshCountdown()` runs after every successful join/leave, and when the timer fires it calls `table.startHand()` with `crypto.randomInt` and broadcasts table + lobby) in a standalone Node process (`npm run realtime`, which refuses to start without `POKER_SERVER_SECRET`) that subscribes to every table's channel plus the lobby channel — no HTTP server, no port, since all traffic is an outbound connection to Supabase's hosted Realtime relay (this is what lets players on different laptops/networks join without any inbound port-forwarding). Unlike Next, this process doesn't auto-load env files, so it calls `dotenv`'s `config()` for `.env` and `.env.local` itself before reading `SUPABASE_*` and `POKER_SERVER_SECRET`. On a table's channel it answers an unsigned `sync` with the state, and otherwise handles only `action` events that pass `verifyRelayedAction()` and whose nonce it hasn't seen (`seenNonces`) — everything else is dropped without an ack. The signed player_id is the identity for `join`, `leave`, and `act`; `act` hands `move`/`amount` to `table.act()`, which does all the validation. The lobby channel only answers `sync`. Joining looks up the player's username via `getPlayerUsername()` (`lib/playerDisplay.ts`), rejects the join if the player is already seated at **any** table (one table at a time — a `joinsInFlight` set per player_id stops two quick joins at different tables from both passing that check during the awaits), validates `buyIn` is an integer in `[50, 200]` times that table's big blind and that the chosen `seatNumber` is open, then deducts it from `players.balance` via `deductBalance()` (an optimistic-lock read-then-conditional-update retried once on a lost race, since PostgREST calls can't share a transaction) before calling `table.join()` — if the seat join itself then fails (e.g. someone else took the seat in the gap), `refundBalance()` immediately gives the money back. Leaving calls `table.leave()` (looked up by the resolved `player_id`, regardless of which tab/connection is asking) and credits the returned chip stack back via `refundBalance()` before broadcasting — unless the ack is `pending` (still in the hand). After anything that can end a hand (`act`, `leave`, the start timer), `settleRemovals()` drains `table.drainRemovals()` and refunds each player removed at the hand's end, then `refreshCountdown()` starts the next hand's countdown. **A dropped connection does nothing** — there is no presence tracking and no disconnect handler, so closing the tab leaves the seat (and stack) exactly as it was; reopening the page shows the same seat via the next `state`/`sync`, and the explicit `leave` action works from that new tab because identity is the signed player_id, not a now-gone connection record. (Full disconnection-timeout removal, SRS-9.x/10.x, is still deferred.) `ack` broadcasts `{ requestId, ok, error?, seatNumber? }` are correlated by `requestId` (Realtime broadcast has no request/reply primitive, so this emulates one); `state` (full `table.getState()`, including each seat's `chipStack`, plus `holeCards` — each dealt-in player's cards sealed with `sealHoleCards()` on every broadcast; the hand starts from the timer use `crypto.randomInt` for both the first button and the shuffle) is broadcast on the table's channel after every successful join/leave and on-demand via a `sync` action for late-joining clients; each join/leave also re-broadcasts the lobby's `state` on `poker:lobby`. Seats carry only a username, never a profile photo: Realtime broadcast has a payload size limit a multi-MB photo can blow past, which silently drops the whole `state` message for everyone — see `GET /api/players/[playerId]/avatar` below.
- `app/poker/usePoker.ts` holds the client hooks both poker pages share: `usePlayerProfile()` (reads `player_token`, loads `GET /api/profile`, which already returns `balance`) and `usePokerChannel(channelName, enabled, onState)`, which subscribes via `getSupabaseBrowserClient()` (`lib/supabase.ts`, a module-level singleton — `createClient()` isn't memoized by Supabase itself, and React Strict Mode's double-invoked effects in dev would otherwise spin up multiple concurrent Realtime sockets), sends `sync` once subscribed, and returns `sendAction(token, request)`, which POSTs to `/api/poker/action` (registering for the ack first, so a fast one can't be missed) and resolves with the matching `ack` from the channel — or an error if the POST fails or no ack arrives within 10 s (e.g. `npm run realtime` isn't running).
- `app/poker/page.tsx` is the lobby (what the home page's Poker button opens). Behind the same "must be logged in" gate as `app/profile/page.tsx`, it subscribes to `poker:lobby` and shows every table, grouped by stakes tier, as a card with a mini table whose seat dots fill in with the live `seatedCount`, plus its blinds, buy-in range and `phase` ("Starting soon" / "In play"), with a Join link to `/poker/[tableId]` (disabled when full). If the lobby state shows the player already seated somewhere (their id in a table's `playerIds`), it `router.replace`s them straight to that table instead.
- `app/poker/[tableId]/page.tsx` is one table (an unknown `tableId` shows a link back to the lobby). It subscribes to that table's channel and sends `join`/`leave`/`act` through `sendAction()` with the player's `player_token` — never a free-typed username, and never on the channel itself. Once per hand it posts its own sealed entry from `state.holeCards` to `/api/poker/hole-cards` and shows the opened cards face up on its seat and large in the controls panel with the current hand's name; other in-hand seats show two card backs. The felt shows the board (five slots) during a hand; between hands it keeps the last hand's board, result line, and each revealed hand (cards plus hand name at the seat, winners' cards ringed) until the next deal. An unseated player clicks an open seat to pick it, then sees a buy-in input clamped client-side to `[50, min(200, balance / bigBlind)] × bigBlind` (the server re-validates this regardless) once the table's `bigBlind` is known from its first `table:state`; the pick is cleared if someone else sits there first. Each seat shows its occupant's chip stack once seated, and a player's own stack is shown next to their Leave button. The felt's center shows "Waiting for players · N/3" (SRS-20.5), then the countdown (rebuilt locally from `countdownMsRemaining` on every `state` and ticked every 250 ms), then the hand number, pot and amount to call; the dealer button (SRS-13.5) and each seat's posted `bet` (labelled SB/BB) sit between the seat and the pot, and a player who sat down mid-hand is dimmed with "Next hand". After a successful join, the page refetches its own balance and calls `notifyBalanceChanged()` (`lib/balanceEvents.ts`), since joining doesn't navigate; after a successful leave it sends the player back to the lobby (`/poker`) — or, for a `pending` leave mid-hand, shows "Leaving after this hand" and navigates once its seat disappears from the state. During a hand the active seat pulses with a "To act" tag (SRS-3.2), seats show their latest action, Folded, or All-in, the felt shows the street, pot, side pots and current bet, and between hands it shows the last hand's result over the countdown. On the player's turn the controls panel renders `app/poker/BettingControls.tsx`: Fold, Check/Call, and Bet/Raise with an amount field, slider and Min / ½ Pot / Pot / All-in shortcuts, all bounded by `getBettingOptions()`; it's re-keyed on every turn so the amount resets. As seats appear in `table:state`, the page separately fetches each occupant's avatar via `GET /api/players/[playerId]/avatar` and caches it client-side by `player_id`, rendering it once it arrives (or an initial-letter fallback until then / if there is none), matching SRS-8.1/8.2.
- `GET /api/players/[playerId]/avatar` returns `{ avatarUrl }` for any player_id, unauthenticated — a seated player's avatar is public to anyone viewing the table, the same as their username (SRS-8.1). This is how the poker page gets avatars now that they're no longer carried through the Realtime broadcast. Unlike `GET /api/profile`, it returns a resized 96×96 thumbnail (via `photoToAvatarDataUrl()`), not the original upload (up to 5MB, SRS-115.3) — seat avatars render under 100px, and serving the full image made the table slow to populate over a bandwidth-limited link (e.g. an ngrok tunnel for cross-network testing).
- `lib/playerDisplay.ts` holds `photoToDataUrl()` (bytea → full-size `data:image/png;base64,...`, used by `GET /api/profile`), `photoToAvatarDataUrl()` (bytea → a 96×96 thumbnail via `sharp`, used only by the avatar route above), `getPlayerDisplay()` (username + full photo, used by `app/api/profile/route.ts`), and `getPlayerUsername()` (username only, used by the poker realtime server's join handler so it never pulls the photo column into a hot path).
